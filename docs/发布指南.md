# Berth 发布指南

本文档描述 Berth 的标准发版流程。**发版一律在本地完成，通过 `scripts/release.sh` 一键执行**，
产物发布到 Cloudflare R2，由 Sparkle 驱动自动更新。

> ⚠️ 不要手动分步执行构建/签名/appcast 各环节，也不要走 GitHub Actions 发版。
> 历史上手动操作曾导致 appcast 链接被改坏、未公证包外发等问题。

---

## 一、前置条件（一次性配置）

| 依赖 | 用途 | 检查命令 |
|---|---|---|
| Developer ID Application 证书 | 代码签名 | `security find-identity -v -p codesigning \| grep "Developer ID"` |
| notarytool 凭据（profile 名 `berth-notary`） | Apple 公证 | `xcrun notarytool history --keychain-profile berth-notary` |
| Sparkle EdDSA 私钥 | appcast 签名 | `security dump-keychain \| grep -i sparkle`（应见 "Private key for signing Sparkle updates"） |
| wrangler 已登录 | 上传 R2 | `wrangler whoami` |

脚本支持的环境变量（一般不用改）：

```
DEVELOPER_DIR     默认 /Applications/Xcode-beta.app/Contents/Developer
SIGN_HASH         默认 72D4152463BB1992518F65C66E8569D29746478B（Developer ID: Yi Xu）
NOTARY_PROFILE    默认 berth-notary
R2_BUCKET         默认 berth-releases
PUBLIC_BASE_URL   默认 https://pub-aa21c73b26d444688ef7db7de0c5f129.r2.dev
```

## 二、发布步骤

### 1. 升版本号

**唯一需要改的地方是 `project.yml`**（Info.plist 的版本字段在构建时被
`MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` 覆盖，手改无效）：

```yaml
MARKETING_VERSION: 0.1.1        # 语义化版本，即 tag/展示版本
CURRENT_PROJECT_VERSION: 3      # 单调递增整数，Sparkle 以此判断新版本，永不回退
```

规则：
- 补丁修复 → patch +1；新功能 → minor +1
- `CURRENT_PROJECT_VERSION` 必须严格递增，**改小会导致老用户收不到更新**

### 2. 执行发版脚本

```bash
./scripts/release.sh
```

脚本会依次完成（全程约 5–10 分钟，公证阶段占大头）：

1. `xcodegen generate` 重新生成工程
2. Release 构建（Developer ID 签名）
3. 重签 Sparkle 嵌套组件（Updater.app / Installer.xpc / Downloader.xpc / Autoupdate / 框架 / 主程序）
4. `codesign --verify --deep --strict` 验签
5. 打包 zip → **公证（notarytool --wait）** → staple → 重新打包
6. 生成 DMG（给手动下载用户）→ 公证 → staple
7. 用 Sparkle 私钥生成签名 appcast（写入 `appcast.xml`，链接指向 R2）
8. wrangler 上传三个文件到 R2：
   - `Berth-$VERSION.zip`（Sparkle 自动更新用）
   - `Berth-$VERSION.dmg`（手动下载/首次安装用）
   - `appcast.xml`

脚本结束时自查一遍输出的 Published 三个 URL。

### 3. 验证发布结果

```bash
BASE=https://pub-aa21c73b26d444688ef7db7de0c5f129.r2.dev

# appcast 已更新且包含新版本条目
curl -s $BASE/appcast.xml | grep "$VERSION"

# zip 可下载，且大小与 appcast 中 length 一致
curl -sI $BASE/Berth-$VERSION.zip | grep -i content-length

# DMG 可下载
curl -sI $BASE/Berth-$VERSION.dmg | head -1
```

下载 zip 解压后本地复核（可选但建议首次做）：

```bash
spctl --assess --type execute --verbose=2 /path/to/Berth.app
# 期望输出: accepted  source=Notarized Developer ID
```

### 4. 提交 appcast

```bash
git add appcast.xml && git commit -m "chore: appcast for v$VERSION" && git push origin main
```

### 5.（可选）打 tag

**注意：推送 `v*` 格式的 tag 会触发 `.github/workflows/release.yml` 的 CI 发版流程，
与本地发版冲突。** 目前采用本地发版，**不要推送 v* tag**；如确需 tag 存档，
先去 Actions 页面确认 Release workflow 不会被误触发（或已禁用）。

## 三、红线（历史上踩过的坑）

1. **不要手动运行 `generate_appcast` 并传 `--download-url-prefix`**——
   它会用新前缀**改写所有已有条目的 URL**，可能把旧版本链接改坏。
2. **appcast 中条目的 `length` 和 `edSignature` 绝不能手改**——
   EdDSA 签名覆盖的是 zip 文件内容，改长度/签名会导致 Sparkle 校验失败。
   只允许改 URL（签名与 URL 无关）。
3. **发布的 zip 必须是公证后重新打包的那份**（脚本第 5 步的第二次打包），
   不能是第一次打包的未 staple 版本。
4. **删除 GitHub Release 后，对应 delta 增量包条目必须从 appcast 移除**，
   否则 Sparkle 拉取失效 delta 直接报"打开安装程序时出现错误"。
5. appcast 里出现指向 GitHub 的 URL 一定是错的，所有 enclosure 都应指向 R2。

## 四、常见问题排查

### Sparkle 报「更新错误！打开安装程序时出现错误」

按顺序检查：

1. `curl -s $BASE/appcast.xml`，确认 enclosure URL 全部指向 R2 且可下载（200）
2. 确认 zip 实际大小 == appcast 的 `length`
3. 本地下载 zip，`spctl --assess` 确认公证有效
4. 确认没有残留指向失效地址的 delta 条目
5. 修复 appcast 后用 wrangler 重新上传：
   ```bash
   wrangler r2 object put berth-releases/appcast.xml --file appcast.xml \
     --content-type application/xml --remote
   ```
   然后让用户重试（Sparkle 下次拉取即拿到修正版）。

### 公证卡在 In Progress

正常，通常 2–10 分钟。超过 30 分钟用
`xcrun notarytool log <submission-id> --keychain-profile berth-notary` 查看详情。

### 升级后版本号没变

检查 `project.yml` 的 `CURRENT_PROJECT_VERSION` 是否真的比线上大——
Sparkle 只比较 build number，不比较 `CFBundleShortVersionString`。

## 五、发布产物速查

| 文件 | 位置 | 用途 |
|---|---|---|
| `Berth-$VERSION.zip` | R2 根目录 | Sparkle 自动更新 |
| `Berth-$VERSION.dmg` | R2 根目录 | 官网/手动下载安装 |
| `appcast.xml` | R2 根目录 + 仓库根目录 | 更新源（R2 为准，仓库同步存档） |
| `.build/dmg/Berth-$VERSION.dmg` | 本地 | staple 后的 DMG 母版 |
